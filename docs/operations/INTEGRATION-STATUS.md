# Integration and customer-journey status

This report distinguishes source capability from external configuration and provider evidence. This documentation update did not inspect account credentials, run tests, perform a remote migration/provider request, or verify a Vercel deployment or Production/Cron execution. `COMPLETE` means source and local test coverage exist for the stated scope; it does not imply tests were run in this batch or a deployed service is ready.

## Status key

- `COMPLETE` — implemented in source with local test coverage for the stated scope; not evidence of deployment or external-provider readiness.
- `NEEDS_CREDENTIALS` — adapter/config path exists; an owner must supply and verify the scoped credentials.
- `NEEDS_PROVIDER_SETUP` — external account, project, or provider-side configuration is still needed.
- `BLOCKED` — the current code/runtime intentionally disables the feature or requires a separate reviewed implementation.
- `NOT_REQUIRED` — not needed for the intended Vercel-hosted path.
- `NEEDS_OWNER_CONFIGURATION` — source support exists, but an owner-controlled identity or environment choice is required before use.

## Customer journey

- **Local synthetic Preview journey:** the focused Vercel adapter test code exercises allowlisted sign-in, draft editing, private preview, a server-priced one-month order, signed SePay Test-mode webhook, fulfillment, and publication with a local SQLite database, in-memory storage, and injected email sink. It does not call external providers or prove deployed Preview behavior; this test was not run in this documentation batch.
- **Local integration harness:** `npm run test:integration` creates one disposable D1 persistence directory under the OS temporary root, binds Wrangler's local Worker and migrations to it, and performs test SQL through that Worker's D1 binding. Any direct Wrangler D1 command is explicitly local and uses the same temporary path; the harness never uses the default `.wrangler/state` database. It covers synthetic signed webhook settlement, duplicate delivery, transaction ownership, API/webhook evidence coexistence, rollback and retry after evidence/payment/order/webhook-outcome/fulfillment-job write failures, and direct/recovery rejection of missing, revoked, mismatched, API-only, and manual-review cases. The SePay D1 contract also checks concurrent lease exclusion, stale-worker fencing and release safety, cursor non-advancement after ownership changes, independent scan modes, UUID/payment ownership collision, and retry after a failed later page. The lifecycle scheduler also includes bounded recovery for persisted SePay webhook events; a focused scheduler regression verifies that a previously received malformed event moves to manual review without paying an order. No provider or remote database is contacted.
- **Preview capability is implemented but not externally verified:** sign-in, media, checkout, settlement, and publication require owner-provisioned Preview resources and complete environment configuration. A missing or mis-scoped value fails closed. Vercel Preview deployment, remote Turso/Cloudinary operation, Resend email, and SePay Sandbox transaction are **NOT VERIFIED**.
- **No public mock mark-paid route exists.** Local mock settlement is only a synthetic test facility.
- **Production readiness:** **NOT PRODUCTION READY**. Production account/provider configuration, current commercial hosting eligibility, deployed runtime, external email delivery, actual payment, and scheduled invocation are **NOT VERIFIED**. SePay Live is not implemented, Production checkout/webhooks are disabled, and Production publication mutations are disabled. The existence of recovery code is not proof of end-to-end Production fulfillment.

See [SETUP-API-CREDENTIALS.md](SETUP-API-CREDENTIALS.md) for exact variable names, environment scopes, and owner actions. Current payment limits are documented in [SEPAY_SETUP.md](../payments/SEPAY_SETUP.md).
