# Crushify Database Schema

**Status:** SQLite schema contract shared by the current Cloudflare D1 backend and the staged Turso/libSQL target. Migrations `0001`–`0010` are applied to local Wrangler D1 by integration tests and an ephemeral Turso/libSQL file database by tests; no persistent or remote database has been migrated.
**Schema baseline:** `schema_migrations` starts at version `1`; each later migration is immutable and transactional where D1 supports it.

**Implementation note:** `migrations/0001_initial_schema.sql` is the baseline; `0002_auth_previews_and_uploads.sql` adds local authentication, preview, upload, rate-limit, and Our Universe v1 seed; `0003_local_test_payments.sql` adds the empty price catalog and payment-review/webhook fields; `0004_payment_webhook_recovery.sql` adds bounded-recovery metadata for verified webhook events; `0008_scheduled_maintenance.sql` adds a persistent Vercel lifecycle lease and run history; `0009_fulfillment_recovery_leases.sql` adds durable fulfillment leases, retry scheduling, and manual-review status while preserving existing jobs; `0010_asset_upload_leases.sql` adds persisted upload-session state and leases for deletion fencing. Business services use a provider-neutral database interface. D1-specific calls remain within the Cloudflare Worker boundary and D1 adapter. The generic `npm run db:migrate:turso` is intended for local files; the separate Vercel staging command requires staging-scoped credentials, explicit operator confirmation, an exact hostname pin, and validates the remote migration ledger before applying checksummed migrations. The Vercel adapter selects Turso using the staging-specific credential pair in Preview and Production-specific variables in Production. No remote Turso migration or D1 data transfer has occurred. Treat applied migrations as immutable.

## 1. Conventions

- IDs are application-generated random UUIDv7 (or at least 128 bits of CSPRNG entropy); never expose sequential rowids as public identifiers. Opaque IDs are not authorization.
- Currency uses ISO 4217 uppercase text (`VND`, `USD`) and monetary values use integer minor units (`amount_minor`). For VND, store whole đồng as the integer; do not use floating point.
- Times are UTC ISO-8601 strings, generated by server. A status update also updates `updated_at`; preserve `created_at`.
- JSON columns contain validated metadata, not media bytes. Keep blobs in R2 and store only object keys, checksums and metadata.
- Enable and verify foreign-key enforcement for each database connection/migration. Use parameterized statements and indexes for lookup paths.
- Hard-delete only under an explicit retention/deletion workflow; financial/audit records may have statutory retention requirements.

## 2. Core migration

The following is a compact starting contract. Production migrations must add any provider/market-specific required fields after review; do not apply this document directly as a deploy script.

```sql
CREATE TABLE schema_migrations (
  version INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  checksum TEXT NOT NULL,
  applied_at TEXT NOT NULL
);

CREATE TABLE customers (
  id TEXT PRIMARY KEY,
  email TEXT NOT NULL,
  email_normalized TEXT NOT NULL UNIQUE,
  display_name TEXT,
  status TEXT NOT NULL CHECK (status IN ('ACTIVE','SUSPENDED','DELETION_PENDING','DELETED')),
  email_verified_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  deleted_at TEXT
);
CREATE INDEX customers_status_created ON customers(status, created_at);

CREATE TABLE templates (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('DRAFT','ACTIVE','RETIRED')),
  current_schema_version INTEGER NOT NULL CHECK (current_schema_version > 0),
  current_renderer_version TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX templates_status ON templates(status);

CREATE TABLE template_versions (
  template_id TEXT NOT NULL REFERENCES templates(id),
  schema_version INTEGER NOT NULL,
  renderer_version TEXT NOT NULL,
  default_data_json TEXT NOT NULL CHECK (json_valid(default_data_json)),
  editor_config_json TEXT NOT NULL CHECK (json_valid(editor_config_json)),
  validation_json TEXT NOT NULL CHECK (json_valid(validation_json)),
  compatibility_json TEXT NOT NULL CHECK (json_valid(compatibility_json)),
  status TEXT NOT NULL CHECK (status IN ('DRAFT','ACTIVE','RETIRED')),
  created_at TEXT NOT NULL,
  PRIMARY KEY (template_id, schema_version)
);

CREATE TABLE designs (
  id TEXT PRIMARY KEY,
  customer_id TEXT NOT NULL REFERENCES customers(id),
  template_id TEXT NOT NULL,
  schema_version INTEGER NOT NULL,
  data_json TEXT NOT NULL CHECK (json_valid(data_json)),
  revision INTEGER NOT NULL DEFAULT 1 CHECK (revision > 0),
  status TEXT NOT NULL CHECK (status IN ('DRAFT','CHECKOUT_LOCKED','PUBLISHED','ARCHIVED','DELETION_PENDING')),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  published_at TEXT,
  FOREIGN KEY (template_id, schema_version)
    REFERENCES template_versions(template_id, schema_version)
);
CREATE INDEX designs_customer_updated ON designs(customer_id, updated_at DESC);
CREATE INDEX designs_template_status ON designs(template_id, status);

CREATE TABLE assets (
  id TEXT PRIMARY KEY,
  customer_id TEXT NOT NULL REFERENCES customers(id),
  design_id TEXT REFERENCES designs(id),
  object_key TEXT NOT NULL UNIQUE,
  rendition_key TEXT UNIQUE,
  visibility TEXT NOT NULL CHECK (visibility IN ('PRIVATE','PUBLISHED')),
  status TEXT NOT NULL CHECK (status IN ('PENDING','QUARANTINED','READY','REJECTED','DELETION_PENDING','DELETED')),
  media_type TEXT NOT NULL,
  byte_size INTEGER NOT NULL CHECK (byte_size >= 0),
  width INTEGER,
  height INTEGER,
  sha256 TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  deleted_at TEXT
);
CREATE INDEX assets_owner_status ON assets(customer_id, status);
CREATE INDEX assets_design ON assets(design_id);

CREATE TABLE orders (
  id TEXT PRIMARY KEY,
  customer_id TEXT NOT NULL REFERENCES customers(id),
  order_type TEXT NOT NULL CHECK (order_type IN ('SELF_SERVICE','CUSTOM_DEPOSIT','CUSTOM_BALANCE','CUSTOM_OTHER')),
  status TEXT NOT NULL CHECK (status IN ('DRAFT','AWAITING_PAYMENT','PAID','FULFILLING','FULFILLED','CANCELLED','REFUND_PENDING','REFUNDED','EXPIRED')),
  currency TEXT NOT NULL CHECK (length(currency) = 3),
  subtotal_minor INTEGER NOT NULL CHECK (subtotal_minor >= 0),
  discount_minor INTEGER NOT NULL DEFAULT 0 CHECK (discount_minor >= 0),
  total_minor INTEGER NOT NULL CHECK (total_minor >= 0),
  coupon_id TEXT REFERENCES coupons(id),
  design_id TEXT REFERENCES designs(id),
  custom_project_id TEXT REFERENCES custom_projects(id),
  idempotency_key TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  paid_at TEXT,
  expires_at TEXT,
  UNIQUE (customer_id, idempotency_key),
  CHECK (total_minor = subtotal_minor - discount_minor)
);
CREATE INDEX orders_customer_created ON orders(customer_id, created_at DESC);
CREATE INDEX orders_status_created ON orders(status, created_at);
CREATE INDEX orders_project ON orders(custom_project_id);

CREATE TABLE order_items (
  id TEXT PRIMARY KEY,
  order_id TEXT NOT NULL REFERENCES orders(id),
  item_type TEXT NOT NULL CHECK (item_type IN ('TEMPLATE_LICENSE','CUSTOM_DEPOSIT','CUSTOM_BALANCE','ADD_ON')),
  reference_id TEXT NOT NULL,
  description_snapshot TEXT NOT NULL,
  quantity INTEGER NOT NULL CHECK (quantity > 0),
  unit_amount_minor INTEGER NOT NULL CHECK (unit_amount_minor >= 0),
  line_total_minor INTEGER NOT NULL CHECK (line_total_minor >= 0),
  metadata_json TEXT NOT NULL DEFAULT '{}' CHECK (json_valid(metadata_json)),
  created_at TEXT NOT NULL
);
CREATE INDEX order_items_order ON order_items(order_id);

CREATE TABLE payments (
  id TEXT PRIMARY KEY,
  order_id TEXT NOT NULL REFERENCES orders(id),
  provider TEXT NOT NULL,
  provider_payment_id TEXT,
  provider_checkout_id TEXT,
  status TEXT NOT NULL CHECK (status IN ('CREATED','PENDING','SUCCEEDED','FAILED','CANCELLED','REFUND_PENDING','REFUNDED')),
  amount_minor INTEGER NOT NULL CHECK (amount_minor >= 0),
  currency TEXT NOT NULL CHECK (length(currency) = 3),
  idempotency_key TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  succeeded_at TEXT,
  UNIQUE (provider, provider_payment_id)
);
CREATE INDEX payments_order_status ON payments(order_id, status);

CREATE TABLE coupons (
  id TEXT PRIMARY KEY,
  code_normalized TEXT NOT NULL UNIQUE,
  status TEXT NOT NULL CHECK (status IN ('DRAFT','ACTIVE','PAUSED','EXPIRED')),
  discount_type TEXT NOT NULL CHECK (discount_type IN ('PERCENT','FIXED')),
  discount_value INTEGER NOT NULL CHECK (discount_value > 0),
  currency TEXT,
  starts_at TEXT,
  ends_at TEXT,
  max_redemptions INTEGER,
  redeemed_count INTEGER NOT NULL DEFAULT 0 CHECK (redeemed_count >= 0),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE custom_projects (
  id TEXT PRIMARY KEY,
  customer_id TEXT NOT NULL REFERENCES customers(id),
  design_id TEXT REFERENCES designs(id),
  status TEXT NOT NULL CHECK (status IN ('INQUIRY','BRIEF_SUBMITTED','QUOTED','QUOTE_EXPIRED','DEPOSIT_PAID','IN_PROGRESS','PREVIEW_READY','REVISION_REQUESTED','APPROVED','BALANCE_DUE','DELIVERED','ON_HOLD','CANCELLED')),
  brief_json TEXT NOT NULL CHECK (json_valid(brief_json)),
  included_revision_rounds INTEGER NOT NULL DEFAULT 0 CHECK (included_revision_rounds >= 0),
  used_revision_rounds INTEGER NOT NULL DEFAULT 0 CHECK (used_revision_rounds >= 0),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  delivered_at TEXT
);
CREATE INDEX custom_projects_customer_created ON custom_projects(customer_id, created_at DESC);
CREATE INDEX custom_projects_status_updated ON custom_projects(status, updated_at);

CREATE TABLE custom_quotes (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL REFERENCES custom_projects(id),
  version INTEGER NOT NULL CHECK (version > 0),
  status TEXT NOT NULL CHECK (status IN ('DRAFT','ISSUED','ACCEPTED','REJECTED','EXPIRED','SUPERSEDED')),
  scope_json TEXT NOT NULL CHECK (json_valid(scope_json)),
  exclusions_json TEXT NOT NULL DEFAULT '[]' CHECK (json_valid(exclusions_json)),
  revision_rounds INTEGER NOT NULL CHECK (revision_rounds >= 0),
  currency TEXT NOT NULL CHECK (length(currency) = 3),
  total_minor INTEGER NOT NULL CHECK (total_minor >= 0),
  deposit_minor INTEGER NOT NULL CHECK (deposit_minor >= 0),
  balance_minor INTEGER NOT NULL CHECK (balance_minor >= 0),
  valid_until TEXT NOT NULL,
  issued_at TEXT,
  accepted_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE (project_id, version),
  CHECK (deposit_minor + balance_minor = total_minor)
);
CREATE INDEX quotes_project_status ON custom_quotes(project_id, status);

CREATE TABLE audit_logs (
  id TEXT PRIMARY KEY,
  actor_type TEXT NOT NULL CHECK (actor_type IN ('CUSTOMER','ADMIN','SYSTEM','PAYMENT_PROVIDER')),
  actor_id TEXT,
  action TEXT NOT NULL,
  entity_type TEXT NOT NULL,
  entity_id TEXT NOT NULL,
  request_id TEXT,
  metadata_json TEXT NOT NULL DEFAULT '{}' CHECK (json_valid(metadata_json)),
  created_at TEXT NOT NULL
);
CREATE INDEX audit_entity_time ON audit_logs(entity_type, entity_id, created_at);
CREATE INDEX audit_actor_time ON audit_logs(actor_type, actor_id, created_at);
```

### Follow-up migration tables (some added locally in migration 0002)

The base schema deliberately leaves out security and operational tables that need their own retention/access policy:

- `customer_sessions`, `login_tokens`, `asset_upload_sessions`, `preview_tokens`, and `auth_rate_limits` exist in local migration `0002`. Login, upload, and preview tokens are stored as hashes; migration `0010` adds `asset_upload_sessions.status` and `lease_expires_at` so deletion can fence active upload work. Production retention/cleanup and rate-limit policy still need operational review.
- `admin_users` or external identity mapping, `admin_sessions` only if Cloudflare Access alone is insufficient.
- `payment_webhook_events(provider, event_id UNIQUE, received_at, processed_at, outcome, payload_hash)`; do not retain full sensitive webhook bodies unless necessary.
- `coupon_redemptions(coupon_id, customer_id, order_id, redeemed_at)` with uniqueness policy to prevent duplicate redemption.
- `design_revisions(design_id, revision, data_json, created_at)` exists locally for optimistic draft history; retention and publication rollback policies remain to be designed.
- `custom_project_events(project_id, from_status, to_status, actor, note, created_at)` for auditable workflow transitions.
- `publications(design_id, published_revision, template_id, schema_version, slug_hash or encrypted slug mapping, status, published_at, revoked_at)`; add a unique index on canonical public slug.
- `idempotency_records(scope, key, request_hash, response_json, expires_at, UNIQUE(scope,key))` for API operations with retries.

`orders` references `coupons` and `custom_projects`, whose DDL appears later in the listing; SQLite permits the forward references. Create all referenced tables before inserting related rows. The order/project relationship is intentionally one-way to avoid a circular foreign key. Add provider-specific transaction uniqueness only after confirming the provider's NULL/retry semantics.

## 3. Relationships and invariants

- Customer owns designs, assets, orders, and custom projects. Every read/write is owner-scoped in Worker queries.
- Design references a specific `(template_id, schema_version)`. A published revision pins the matching renderer version; never silently migrate a live gift.
- Order price and item description are snapshots taken from the server-side catalog/accepted quote. Recompute totals on the server and require `total = subtotal - discount`.
- Payment is append-only by attempt; a failed retry creates a new payment attempt, not a forged update of an old provider transaction.
- A custom quote is immutable once issued. A changed scope/price/revision limit produces a new version and marks the prior quote `SUPERSEDED`.
- Coupon redemption and order creation must be transactionally/idempotently guarded; increment count only once on the selected business event.
- Audit logs are append-only for application paths. Restrict access, redact secrets/PII, and set a reviewed retention policy.

## 4. State transitions

`orders`: `DRAFT → AWAITING_PAYMENT → PAID → FULFILLING → FULFILLED`; alternate terminal/exception paths: `CANCELLED`, `EXPIRED`, `REFUND_PENDING → REFUNDED`. Provider failure leaves order awaiting payment or permits expiry; it does not mark the order paid.

`payments`: `CREATED → PENDING → SUCCEEDED | FAILED | CANCELLED`; refund path `SUCCEEDED → REFUND_PENDING → REFUNDED`. Only a verified provider event or audited admin reconciliation may set success/refund state.

`fulfillment_jobs`: `PENDING → PROCESSING → COMPLETED`; failed work becomes `FAILED` with a bounded exponential retry time, and exhausted retries become `MANUAL_REVIEW`. Claims use an atomic expiring lease with a per-claim fencing token. Fulfillment eligibility is independently rechecked against the settled payment and processed webhook evidence. Retry attempts never create or settle a payment.

`assets`: `PENDING → QUARANTINED → READY` or `REJECTED`; deletion uses `DELETION_PENDING → DELETED`.

Custom project transitions and guard conditions are specified in [CUSTOM_DESIGN_WORKFLOW.md](CUSTOM_DESIGN_WORKFLOW.md).

## 5. Versioning and migrations

- Check `schema_migrations` before applying numbered forward migrations; the Turso migration runner validates checksums, applies each migration transactionally, verifies foreign keys, and fails closed on unknown or untracked schema state.
- Never edit an applied migration. Add a new migration and a tested rollback/forward-recovery plan. Prefer expand → backfill → contract.
- Keep sample data and local test databases separate from production. Back up before destructive schema/data operations and run a restore drill.
- `schema_version` is per template data contract; database schema version is the migration number. These version axes are independent.

## 6. Database adapter contract and tests

`src/database.ts` defines the common prepared-statement, result, batch, and normalized-value contract. `src/database/d1.ts` adapts Cloudflare D1; `src/database/turso.ts` adapts `@libsql/client`. `DATABASE_PROVIDER` must explicitly be `d1` or `turso`. The Cloudflare Worker currently accepts only D1. The Vercel API adapter uses the Turso provider after fail-closed environment and database configuration validation; Preview maps only `TURSO_STAGING_DATABASE_URL` and `TURSO_STAGING_AUTH_TOKEN` into the generic provider interface, while Production uses only `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN`. This code-level selection does not verify remote account ownership, database identity, or token scope.

Both adapters normalize booleans to SQLite integers, `Date` values to UTC ISO strings, preserve `null`, and reject `undefined` and non-finite numeric parameters. The libSQL adapter maps constraint and busy errors to shared error codes, maps `RETURNING` rows and result metadata, and submits write batches as atomic libSQL batches. Foreign-key enforcement is enabled and checked on each Turso connection.

`tests/database-contract.mjs` runs the same API-level flows against Wrangler local D1 and a temporary local Turso/libSQL file database: magic-link request/consume and replay rejection, session authentication, customer ownership, design create/read/update/reload, stale-revision `409`, preview bearer access, asset metadata/storage lifecycle and ownership checks. D1 integration injects a failing revision write and verifies the preceding design update was rolled back; both engines also test foreign-key and unique constraints. Turso adapter tests additionally cover atomic batch rollback, `RETURNING`, insert metadata, and parameter normalization. Current verified results are recorded in [HOSTING_MIGRATION.md](HOSTING_MIGRATION.md). The D1 integration test includes the legacy API regression suite; automated Turso tests use local files only. The Vercel provider-selection tests use synthetic environment objects and do not connect to remote Turso.

## 7. D1 data export/import boundary

Schema migration and data migration are separate operations. The checked-in migration runner handles schema only; no D1-to-Turso data importer exists, and no data has been transferred. Before any future transfer, classify records to retain, regenerate, revoke, or exclude (in particular sessions, login tokens, rate-limit rows, upload capabilities, and preview tokens). Export sensitive SQL outside the repository to encrypted storage, import only into an explicitly verified empty test target, compare per-table counts and key relationships, run foreign-key and uniqueness checks, and rehearse restore before requesting approval for any remote operation. A detailed gated runbook is in [HOSTING_MIGRATION.md](HOSTING_MIGRATION.md).

## 8. Local payment schema extension

Migrations `0003_local_test_payments.sql` and `0004_payment_webhook_recovery.sql` are forward-only and add:

- `template_prices`, keyed by template/schema version, with VND integer amounts and at most one active row. It is intentionally empty: no product price has been approved or activated.
- Nullable order/payment references, the purchased design revision, an idempotency request hash, and manual-review flags. Existing `orders.status` and `payments.status` checks remain unchanged; API responses expose `MANUAL_REVIEW` when the review flag is set.
- `payment_webhook_events.raw_payload` and `review_reason`, retaining the exact decoded webhook JSON and its SHA-256 hash for audit/reconciliation. Restrict database/log access and define retention before production.
- Migration 0004 adds a processing-attempt count/time, provider transaction ID, linked order reference, expected and actual integer amount, plus an index for finding unresolved `RECEIVED` events. The bounded internal recovery service retries these events; no public recovery endpoint or scheduled runner is configured.

The local self-service order path snapshots the active template price and draft revision into the existing order/item/payment tables. Tests insert a clearly synthetic VND 50,000 price into disposable D1/Turso databases only. Migrations 0003–0004 insert no catalog rows, do not alter existing customer records, and have not been applied to remote D1/Turso.

## 9. Fulfillment recovery schema

Migration `0009_fulfillment_recovery_leases.sql` rebuilds `fulfillment_jobs` to add `MANUAL_REVIEW` and nullable `next_attempt_at`, `lease_token`, `lease_expires_at`, and `last_failure_at` columns. It copies all prior job identifiers, statuses, attempt counts, error codes, timestamps, and order references; existing `PROCESSING` jobs without a token are reclaimable by the new code. A recovery index covers status and due/lease timestamps. No migration is run against remote databases in this change. The migration is forward-only; if deployment reveals a problem, preserve the data and apply a reviewed forward repair rather than editing or reversing the applied migration.

Automatic retry policy is eight attempts, starting at 30 seconds and doubling to a one-hour maximum delay. Expired claims are reclaimable, and a per-attempt random lease token prevents stale workers from finalizing a replaced claim. `last_error_code` stores only a fixed safe category, not raw exception messages. `MANUAL_REVIEW` remains visible through the order's fulfillment status and Worker scheduled-run counts. This schema does not add an operator recovery endpoint or enable a scheduler; deployed activation remains subject to existing environment and payment gates.

## 10. Local-only publication and delivery schema

Migration `0005_publication_delivery.sql` adds the local Phase 6 publication model. It rebuilds the earlier `publications` table to add the owning design/order, pinned template/schema/renderer versions, immutable snapshot JSON, status, lifecycle revision, optional expiry, and publication timestamps. Legacy rows are preserved as `UNPUBLISHED` with no public slug, empty snapshots, and renderer version `unsupported`; they cannot be served by the new renderer.

`publications.slug_hash` stores the hash used for public-route lookup; the separate random `slug` value is also retained in D1 so the owner dashboard can reconstruct the recipient URL. Treat the D1 field and backups as bearer-link secrets and restrict access accordingly. A partial unique index allows one reissuable publication per design, and indexes cover design/status and expiry lookups. Publication creation links to the paid order; the runtime additionally rechecks the order item, payment, processed webhook event, amount/currency, owner, design revision, and active template/version before publish and public reads.

`publication_assets` records per-publication, per-asset consent and derivative lifecycle (`PENDING`, `READY`, `CLEANUP_PENDING`, `DELETED`). The source `assets` object remains private. Consent withdrawal, unpublish/revoke, expiry, and design deletion deny access immediately; derivative cleanup failures remain marked for a later retry. Image bytes are never stored in D1.

The migration seeds schema-v1 template/version metadata and defaults for Love Letter, Our Memories, Say Yes!, and Distance Means Nothing; Our Universe already has its registry entry. All five server validators and renderer mappings are code-owned. This migration and the publication mutation API have only been run in local test databases; do not infer staging or production readiness from local migration history.

## 11. Upload/deletion coordination

Migration `0010_asset_upload_leases.sql` adds the upload-session states `PENDING`, `UPLOADING`, `COMPLETE`, and `CANCELLED`, plus a lease expiry for in-flight storage writes. Upload grant creation, upload claims, storage-finalization metadata, and design deletion use conditional SQL writes and adapter batches. Deletion refuses to transition a design while an unexpired upload lease exists, and physical archival is conditional on every source asset being marked `DELETED`. Expired upload leases are cancelled during a deletion retry; the storage object is then cleaned through the existing idempotent retry path. D1 batches and Turso/libSQL write batches provide the SQLite transaction boundary used for these state changes. This migration is forward-only and has not been applied to any remote database.
